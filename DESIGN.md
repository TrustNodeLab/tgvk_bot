# Дизайн: SMM-студия TrustNode (Cloudflare Worker + GitHub)

## Цель
Автономная публикация постов **с карточками**, работающая даже при аутэдже GitHub.
Бесплатно, без привязки карт, без всегда-включённой своей машины.

## Принцип
Карточку не обязательно рисовать в момент поста. Готовые посты (текст + PNG)
заранее складываются в «склад» (Cloudflare KV/R2). Публикация — это просто
HTTP-загрузка готового PNG, что Worker делает без тяжёлого CPU.

## Два контура

### Контур подготовки (GitHub Actions — когда GitHub жив)
- Worker-крон (каждые 5 мин) сканирует 51 фид, **дедуплицирует** одинаковые
  новости, кладёт кандидатов в очередь KV и диспатчит их в GitHub Actions.
- GitHub Actions (workflow_dispatch): GigaChat-анализ (с суммаризацией
  пересекающихся тем) -> рендер карточки (Pillow) -> готовый пакет поста
  (JSON + PNG) загружается в «склад» через Worker API.
- Плановый контент (ежедневный аудит, воскресный недельный аудит,
  понедельничный ивент) тоже готовится GitHub'ом заранее и кладётся на склад.

### Контур публикации (Cloudflare Worker — работает всегда)
- Планировщик в Worker: по наступлению слота берёт готовый пост со склада и
  публикует в TG + VK. Worker только загружает PNG (чистый HTTP).
- Admin-поток: черновик с кнопками ✅/🕐/❌. Нет ответа 30 минут -> пост уходит
  в ближайший свободный слот (отложенный).
- Аварийный фолбэк: если диспатч в GitHub «завис» (GitHub лежит) — Worker
  публикует редкий текстовый «аудит-пост» (заголовок + ссылка), пока склад
  пополняется. Спам исключается кулдауном.

## Расписание слотов (МСК, с лёгким разбросом внутри окон)
- 06:00–12:00 -> до 2 новостных постов
- 12:00–17:00 -> до 1 новостного поста
- 17:00–22:00 -> до 2 новостных постов
- ~21:30 -> ежедневный аудит («что было сегодня»)
- Воскресенье ~21:00 -> недельный аудит («самое интересное за неделю»)
- Понедельник ~20:00 -> ивент (каждый раз другой формат)

## Дедуп и суммаризация
- Нормализация заголовка (регистр, пунктуация, суффиксы «— Издание»).
- Схожесть по токенам (Jaccard, порог ~0.7 = та же новость).
- Из группы дублей берём источник с наибольшей подробностью (длиннее текст).
- Обобщение нескольких новостей про одно событие — через LLM в контуре
  подготовки (кандидат передаёт кластер связанных ссылок).

## Свежесть
Окно 1–2 дня, приоритет последним ~6 часам, чтобы склад не отдавал старьё.

## Ограничения (заложены)
- **GigaChat из Worker нельзя** — CA Сбера (НУЦ Минцифры) нет в доверенных у
  Cloudflare. Поэтому LLM только на GitHub.
- Free Worker: <=50 подзапросов/вызов -> скан дробится (по ~25 фидов за крон,
  цикл из 2 крон). CPU 10 мс -> Worker не рисует и не парсит тяжело (только
  лёгкий дедуп + постинг).
- Репо public (безлимит минут Actions), `data/` вычищен из git.

## Хранение (KV)
- `state` — настройки: seen_guids, autopost, dry_run, blacklist, ключевые слова,
  счётчики, кулдауны аудитов.
- `candidates` — очередь сырых кандидатов на подготовку.
- `stock` — очередь готовых к публикации пакетов.
- `draft:<id>` — черновики на ручном апруве.
- `publish_log` — история публикаций (для аудитов, /stats, /export).
- `dispatch:<guid>` — отслеживание диспатчей в GitHub (для фолбэка).

## Админ-интерфейс (TG-бот в Worker)
/start /help /status /sources /schedule /draft /publish /skip /audit /stats
/blacklist /keyword /test /settings /export /dryrun /rescan /version /menu

## Тестирование
- Dry-run режим: полная симуляция публикации без отправки в реальные каналы.
- Модульные тесты Worker (node:test, стаб KV/R2/fetch), Python-тесты (unittest,
  мок GigaChat/TG/VK), E2E-симуляция без реальных публикаций.
